A small, working permissions system for AI agents

actas

When an AI agent works for you, what stops it from doing more than you allowed? Actas gives each agent a pass that can only get smaller as work is handed on, runs out quickly, and leaves a record of who did what.

The problem

Agents pass work on.You ask an assistant to check your calendar. It hands part of the job to a helper. Today the helper often inherits your full access.
Access should shrink, not grow.Each hand-off should carry fewer permissions and a shorter life. Asking for more than you were given should simply fail.
You need a trail.If something goes wrong, you want to know which agent acted for whom, and be able to switch one off and everything it handed out with it.

What is real, what is not

    

      
Real, runs on every click
The token exchange, scope narrowing, lifetime limits, RS256 signing, proof-of-possession checks, revocation of a token and everything derived from it, and the hash-chained audit log. Nothing on this page is pre-recorded.

      
Made up
Asha, the agents, the calendar and notes services, and their data. Each lab run uses a fresh throwaway service. Your policy workbench inputs are separate from this fictional world and are not stored by the application.

      
Not claimed
No login or consent screen, no independent security audit, not production ready. Proof of possession is a subset of the spec, and its single-use tracking works per server instance only. The audit chain shows tampering; it does not prevent it.

    

  


  

    What this is. A runnable reference implementation of OAuth 2.0 Token Exchange
    (RFC 8693) built from public specifications, with RS256 JWTs (RFC 7519), a JWKS endpoint
    (RFC 7517), and a hash-chained audit log. The hash chain is tamper-evident: it detects
    edits to recorded history. It is not tamper-proof storage, and this server is not a
    production authorization server.
